# AGENTS.md — E2Engine Go Instrumentation

## Project

This repository provides lightweight Go instrumentation for propagating E2Engine test execution IDs through applications and dependency calls. It is a multi-module repository, not a single Go module:
- . — github.com/e2engine/instrumentation-go: context primitives and ID validation.
- http/ — HTTP inbound/outbound instrumentation.
- grpc/ — unary gRPC inbound/outbound instrumentation.
- aws/ — AWS SDK for Go v2 instrumentation; aws/lambda/ contains API Gateway HTTP API v2 Lambda support when present.

Review the current files and module manifests before editing. Do not assume that a planned package, API, or implementation already exists.

## Execution ID contract
- An E2Engine test execution ID is exactly 64 lowercase ASCII alphanumeric characters, matching [a-z0-9]{64}. IDs generated by E2Engine may be hexadecimal, but validation must not be narrowed to hexadecimal unless the shared contract changes.
- Use e2engine.ValidTestExecutionID(id) for validation; do not reimplement the rule in adapters.
- e2engine.WithTestExecutionID(ctx, id) returns the same context for invalid or empty IDs; if a valid ID was already present, it remains intact.
- e2engine.TestExecutionID(ctx) returns the ID or an empty string. The root context setter is the normal entry point for validated IDs.
- Execution IDs are correlation metadata, not authorization or authentication credentials. Do not assume possession of an ID proves caller identity.

## Inbound propagation
- Accept exactly one valid execution ID from inbound HTTP headers or gRPC metadata.
- Ignore missing, empty, invalid, or multiple ID values; do not fail the application request solely because its ID is invalid.
- Preserve the existing context and original request when extraction cannot accept an ID. A valid inbound ID may replace an ID previously present in context.
- Do not alter unrelated headers/metadata.

## Outbound propagation and precedence
  For instrumented outgoing requests, explicitly supplied metadata takes precedence over context:
1. If outgoing HTTP headers or gRPC metadata contain exactly one valid execution ID, preserve that ID, even if context contains a different valid ID.
2. If the outgoing ID is missing, invalid, or ambiguous (multiple values), use a valid ID from context.Context if available.
3. If neither source offers a valid ID, remove malformed/ambiguous execution-ID metadata; otherwise leave the request unchanged.
4. Never propagate invalid or ambiguous IDs.
   Consequently, a valid manually supplied outgoing ID is an explicit override. Ensure implementations and tests document this precedence. Apply the same policy to AWS outgoing instrumentation when modifying it, subject to AWS transport/signing requirements.
- HTTP Inject must never mutate the supplied *http.Request or its headers; clone only when changes are necessary. A no-op should return the original request.
- Use conventional http.Header operations and canonical keys. Direct writes of noncanonical map keys are outside the adapter's normalization responsibility; do not rewrite intentionally noncanonical keys without discussing a policy change.
- gRPC Inject must preserve unrelated outgoing metadata and avoid accumulating duplicate execution-ID entries. Use copies when modifying metadata.MD and do not mutate caller-owned metadata.
- Lower-level HTTP/gRPC TestExecutionID helpers expose raw metadata values, not a validated guarantee.
- Lower-level WithTestExecutionID metadata/header helpers return a copy: valid IDs replace existing values; invalid or empty IDs remove the execution-ID key. WithoutTestExecutionID also returns a copy with the key removed.
- AWS SDK propagation occurs at the Smithy Build stage, before SigV4 signing. Verify precedence and cleanup without moving header changes after signing.

## Go and dependencies
- Each subdirectory listed above has its own go.mod. Do not treat a dependency of one module as a dependency of all modules.
- Maintain the lowest supported secure Go version per module, rather than bumping every module for consistency. The gRPC module has been moved to Go 1.26 because of its updated dependency graph; inspect each other module's go.mod before stating its minimum.
- Prefer the Go standard library and existing dependencies. Avoid adding logging, telemetry, or configuration dependencies for routine propagation.
- Future consideration, not for the current release: opt-in notifications of invalid-ID removal (possibly a WithLogger option). Do not introduce that API or log raw untrusted IDs without an explicit design decision.

## Tests and verification
- Use table-driven Go tests when helpful; cover both behavior and preservation of original objects.
- Use valid 64-character fixtures for successful propagation. Legacy examples such as execution-123 are invalid and should appear only in negative tests.
- Cover: missing, empty, malformed, uppercase, too-short, too-long, and multiple IDs; preexisting valid context IDs; explicitly supplied valid outgoing ID overriding context; invalid outgoing ID replaced by valid context; invalid outgoing ID removed when no fallback exists; unrelated metadata unchanged; original objects unmodified.
- Test both direct helper functions and wrapper/interceptor behavior where applicable, including response/error passthrough.
- Execute tests per module because the repository contains independent go.mod files. From a module directory: go test ./... -count=1; for concurrency-sensitive changes: go test -race ./... -count=1.
- From the repository root, use make test, make test-race, or make verify as appropriate. Check the current Makefile and selected toolchain: not every module necessarily supports the same minimum Go version. GOTOOLCHAIN=local avoids automatic toolchain upgrades when checking compatibility.
- Do not claim tests passed unless they were actually executed; report failures and environment limitations precisely.
